## 1. Executive recommendation

1. **Improve enforcement integrity before adding more scores.** The requested “zero trust in the running agent” is not Superman v0's accepted architecture: its checker runs from the candidate PR, with tests and André's review as its trust boundary. An independently governed evaluator, isolated project execution and an external admission publisher require a **new human-reviewed Gate 1 architectural decision**, not another lint command. Even that design provides independently enforced, bounded evidence—not zero-trust proof of correctness. [README][local-readme], [ADR 0001][local-adr1], [SLSA 1.2][slsa], [GitHub attestation limitation][gh-attest]
2. **Keep the existing coverage contract honest:** **90% minimum separately for lines, statements, branches and functions; 100% target**, over the complete owned-code inventory. Neither number establishes TDD, assertion quality or requirements correctness. Preserve G9's meaningful red-on-base/green-on-candidate replay and strengthen risk-specific behavioral/negative tests; do not manufacture coverage by excluding difficult code. Per-file floors, changed-line floors and an automatic coverage ratchet are **optional new policies, explicitly not selected in ADR 0014**. [Spec §5.4][local-spec], [coverage policy][local-coverage-policy], [ADR 0014][local-adr14], [coverage study][coverage-study]
3. **Reuse the TypeScript stack rather than install overlapping suites.** Keep tsrs/reference TypeScript, Biome, Archgate, Vitest, Knip, jscpd, Stryker and Trivy. Biome already supplies cognitive-complexity, function-length, parameter-count and import-cycle rules. Start structural rules as visible diagnostics; promote only calibrated, useful rules through Gate 1, with explicit failing severity and negative fixtures. Do not add ESLint/Sonar/Semgrep/a separate complexity suite merely to count the same things again. [Package pins][local-package], [pinned Biome rules][biome-cognitive-src], [length][biome-lines-src], [parameters][biome-params-src], [cycles][biome-cycles-src]
4. **Block high-signal violations; use maintainability proxies to direct attention.** Type errors, failed required behavior, forbidden dependency edges, invalid evidence and approved security-policy findings warrant hard gates. A cognitive score of 16, a 51-line function or five parameters is not by itself a correctness/security defect. The familiar **15 / 50 / 4 are Biome defaults, not universal scientific boundaries**. Avoid forcing shallow helpers, options bags or needless abstractions to satisfy them. [Biome docs][biome-cognitive], [length][biome-lines], [parameters][biome-params], [NIST §§2.5, 9][nist-pdf]
5. **Retain protected no-regression ratchets, but expose individual regressions and new-code weakness.** Current G6 accepts a new file as measured initialization without an absolute mutation floor. A low initial score can persist; an average can hide a lost critical assertion behind easy new kills. Recommend explicit review of introduced survivors and critical behaviors, with any calibrated new-code mutation policy separately approved. Do not invent a universal 80/90/100 mutation floor. [Quality driver][local-quality], [spec §§5.3–5.4][local-spec], [mutation evidence][mutation-study]
6. **Do not confuse nightly detection with pre-merge prevention.** Keep bounded PR analysis plus uncached full nightly checks, but identify what each actually measured. The planned affected-mode duplication blind spot is an accepted v0 limitation, not a complete pre-merge guarantee. For strict pre-merge clone enforcement, compare changed code against the whole approved corpus, or run the full scan; budgets cannot turn an incomplete required gate into a pass. [Spec §§5.4, 5.7][local-spec], [bootstrap G5/G6 evidence][local-bootstrap-evidence], [jscpd source docs][jscpd-docs]

**Decision order:** finish existing Gate 1 prerequisites; decide whether to retain the explicitly human-trusted v0 or reopen its evaluator boundary; then calibrate and approve additional policies. Nothing here admits ticket 01. [README][local-readme]

### Read-only local pilot: the structural rules are not already hard gates

Parent-session observations on the HEAD above, on 2026-11-01; no fixes or permanent configuration changes. Scope was **31 bootstrap/rule files, including tests**, not product source:

```text
node_modules/.bin/biome lint --reporter=summary .superman/ci .archgate/adrs
→ exit 0; 31 files; no diagnostics

node_modules/.bin/biome lint --only=complexity/noExcessiveCognitiveComplexity --only=complexity/noExcessiveLinesPerFunction --only=complexity/useMaxParams --max-diagnostics=none --reporter=summary .superman/ci .archgate/adrs
→ exit 0; 22 cognitive-complexity info + 20 function-length info + 5 parameter warnings
```

That is **47 diagnostics across 13 files**, not 47 proven defects. A further cognitive-only run with `--error-on-warnings` still exited 0 with 22 **info** diagnostics. Thus even that flag does not make an informational rule blocking: explicit `level: "error"` plus a failing fixture would be needed for a new hard policy. Biome documents `--error-on-warnings` as affecting warnings, not information. [CLI][biome-cli], [pinned rule metadata][biome-cognitive-src]

Parent pilots for the pinned `nursery/noFloatingPromises`, `nursery/noMisusedPromises` and `suspicious/noImportCycles` commands also exited 0 without diagnostics over those 31 files. They establish observed command compatibility only—not complete type/graph coverage or absence of bugs. These pilot results were supplied by the parent, not independently reexecuted by this researcher.

## 3. What the examples measure—and what the evidence supports

| Example | Primary-source fact | Decision implication / limitation |
| --- | --- | --- |
| Coverage | Inozemtseva & Holmes, **ICSE 2014**, studied **31,000 suites over five large Java systems**, using mutation effectiveness. After controlling for suite size, correlation was generally low to moderate and project-dependent; stronger coverage criteria did not reliably improve the relationship. [Paper, abstract/§8][coverage-study] | Useful for identifying untested code; not a correctness score. This is older Java evidence, not an estimate of this TypeScript harness or 2026 agent-generated code. It neither proves coverage useless nor scientifically selects 90 or 100. |
| Mutation | Just et al., **FSE 2014**, studied **357 real faults in five Java applications** and found association between mutant and real-fault detection beyond coverage. Common operators coupled to **73%** of those faults; **27%** were not coupled. [Paper, §§3, 5][mutation-study] | Mutation adds useful test-sensitivity evidence but has operator/model blind spots. Do not translate that result into a guaranteed detection rate, TypeScript threshold or proof of correctness. |
| Cyclomatic complexity | NIST SP 500-235 defines single-module control-flow complexity as **edges − nodes + 2**, corresponding to independent basis paths, not all feasible executions. Its §2.5 recommends 10 with justified departures, acknowledges successful limits as high as 15, and warns about gaming modified metrics. [1996 report, §§2.2–2.5][nist-pdf], [publisher record][nist-record] | A control-flow/testing-effort signal, not interchangeable with cognitive complexity or function length. “10” is a contextual historical recommendation, not a universal theorem. Branch coverage can be achieved with fewer tests than a basis set; neither establishes behavior correctness. |
| Cognitive complexity | SonarSource's **white paper v1.7, 2023-08-29**, defines a judgment-based understandability measure with nesting/flow-break increments. Biome's implementation has default maximum **15** and is **not recommended/enabled by the recommended preset**. [White paper][cognitive-paper], [pinned Biome source][biome-cognitive-src] | Algorithm specification and vendor default are not independent scientific validation of a universal cutoff. Use the exact tool's semantics; do not call the number cyclomatic complexity or compare different implementations without fixtures. |
| Function LOC / parameters | Biome defaults are **50 function-body lines** and **4 parameters**; these rules are also not recommended. Length defaults count blank lines and do not exempt IIFEs. [Docs][biome-lines], [parameters][biome-params], [pinned sources][biome-lines-src] | Size/interface prompts, not defect proofs. Document body/declaration/comment/blank-line conventions. An options bag can hide many independent inputs; tiny helper chains can hide a difficult algorithm. NIST explicitly warns that splitting without cohesive responsibilities can worsen coupling/design. [NIST §§2.5, 9][nist-pdf] |
| Afferent/efferent coupling | Incoming (**Ca**) and outgoing (**Ce**) dependencies measure different directions. NDepend's documented assembly metrics count external **types**; its instability formula is `Ce / (Ca + Ce)`. [Metric definitions][coupling-docs] | If adapted to TS modules/packages, specify the unit and edge model rather than claiming those .NET counts are identical. High incoming coupling may identify an intentionally stable API; outgoing coupling may be legitimate orchestration. No universal maximum or ideal ratio is established here. |
| Churn/hotspots | Nagappan & Ball, **ICSE 2005**, found relative churn measures more useful than absolute churn in their Windows Server 2003 case study; the paper explicitly limits generalization across contexts. [Original paper, §§3–5][churn-paper] | Rank review/test investment, not merge eligibility. Do not transplant its reported classifier accuracy to this young TS repo, treat every frequently changed file as defective, or penalize necessary repairs. |
| Static-analysis warnings | Sadowski et al., **CACM 2018**, describe different criteria for compiler-blocking checks and code-review suggestions, emphasizing actionability and developer feedback. Their review-check false-positive cutoff was an operational choice, explicitly initially somewhat arbitrary. [Original article, pp. 58–64][static-study] | Choose high-signal blocking rules and measure local usefulness. Neither “all available rules on” nor another organization's numerical default is an evidence-based universal quality bar. |

**Synthesis:** metrics constrain observable properties, not whether the implementation meets its requirements. Passing every listed check can coexist with a missing requirement, wrong authorization decision, weak oracle, unmodeled dependency or deliberately test-aware implementation. The justified goal is **independently enforced constraints plus stronger behavioral evidence**, with a stated trusted computing base—not “a score proves state-of-the-art correctness.” [Coverage/mutation studies][coverage-study], [mutation study][mutation-study], [TypeScript soundness note][ts-soundness], [GitHub attestation warning][gh-attest]

## 5. Coverage: keep the denominator, semantics and provenance visible

### Existing policy—not “90% TDD”

For each metric independently, compute `sum(covered items) / sum(total items)` over the same complete inventory. Do not average file percentages, combine the four percentages into one quality number, or accept a rounded displayed 90 when the actual count ratio is below 90%. **100% remains the target, not the current hard minimum.** ADR 0014 deliberately selected overall floors without an automatic ratchet. [Spec §5.4][local-spec], [ADR 0014][local-adr14]

- **Line coverage** says measured executable lines ran; **statement coverage** counts measured statements; **function coverage** says measured functions ran; **branch coverage** says measured branch outcomes ran. One does not substitute for another, and branch coverage is not complete path coverage, MC/DC or proof of assertions. Measurement is conditional on the provider's mapping/branch model. [Vitest configuration][vitest-coverage-config], [NIST §§2, 5][nist-pdf]
- **Overall versus per-file:** a high aggregate can conceal a poorly tested critical module. Report per-file/function gaps and require identified critical behavioral tests. A per-file floor would be a different policy with different small-file/zero-item behavior—not a correction the agent can silently make. [ADR 0014][local-adr14]
- **Changed-line coverage** is a separate view: define executable added/modified source lines, rename/remap treatment and how changed branches/functions are selected. Deleted lines and a diff with no executable lines need explicit semantics. It is useful feedback but cannot satisfy Superman's overall floor. If later adopted as a gate, it needs its own reviewed denominator and evidence contract. [Existing overall contract][local-spec], [Vitest `coverage.changed`][vitest-coverage-config]
- **TDD evidence:** executing code is not demonstrating an assertion or demonstrating tests were authored first. G9 deliberately checks behavioral red–green replay, not timestamps/authoring order. Retain that precise claim. [Spec G9][local-spec]

### Inventory and instrumentation failure are gate failures, not good percentages

Vitest 5.0.5's documented default includes only files imported by tests; `coverage.include` is needed to include unexecuted files. Its V8 implementation uses AST-based remapping, but this does not independently establish Superman's multi-process/rule inventory, correct source bytes or complete collection. Current bootstrap specifically handles those seams rather than simply trusting the default Vitest report. [Pinned guide][vitest-coverage-guide], [collector][local-coverage], [ADR 0014][local-adr14]

**Recommendation:** retain/verify a protected inventory of all owned runtime, bootstrap and actual rule code; compare expected versus reported canonical files and source hashes. Treat unknown roots, disappearing files, unapproved exclusions/ignore directives, unsupported remapping, truncated child/worker collection, stale profiles and missing report identities as incomplete evidence. Never accept “0 of 0” or an empty report as a manufactured 100%; distinguish a legitimate zero-item dimension (for example, a file with no measurable functions) from an absent analysis. Tests-only fixtures/declarations/generated files need a reviewed classification, not an author-controlled escape label. [Existing contract and demonstrated unloaded-module denominator issue][local-adr14], [Vitest include/exclusion/ignore controls][vitest-coverage-guide]

Fresh measurements of changed code plus verified unchanged-code coverage can satisfy the spec only when **all invalidating inputs** are modeled: source, tests, fixtures/snapshots, dependency/selection graphs, config, tools, runtime/instrumentation, relevant environment and trusted producer identity. Test changes can invalidate coverage of unchanged source. A prior green report or changed-files-only result is insufficient. Unknown/stale inputs require the uncached full fallback; bootstrap reuse is currently off, and nightly is full. [ADR 0014][local-adr14], [spec §§5.4–5.7][local-spec]

That is a measurement contract, not a claim that an adversarial same-process program cannot forge counters; §7 addresses the stronger threat model.

## 6. Mutation: explicit denominators, conservative outcomes, bounded execution

### Upstream metric versus Superman's actual metric

Stryker's documented general metric is:

```text
detected = Killed + Timeout
valid = Killed + Timeout + Survived + NoCoverage
native mutation score = detected / valid × 100
```

Runtime/compile errors do not enter that native score; ignored/pending mutants also do not contribute to the valid denominator. Its **covered-code** score additionally excludes `NoCoverage` from the denominator, and can therefore look better while untested mutants remain. Always label which score is reported. [Mutant states and metrics][stryker-metrics]

**Current local contract is deliberately stricter:** `quality.ts`, lines 401–509, counts all statuses, rejects **any CompileError, RuntimeError, Timeout, Ignored or Pending**, rejects zero/inconsistent instrumented counts, and computes **`Killed / totalMutants × 100`** only after validating completion/source/test identities. `Survived` and `NoCoverage` remain undetected outcomes. Do not silently replace this with Stryker's native calculation or count local timeouts as successes. [Actual driver][local-quality]

**Recommendation:** preserve separate counts for every status, mutator, file, scope and survivor; explicitly diagnose infrastructure/resource timeouts versus mutant-induced hangs. Native Stryker counts the latter as detected, but Superman currently rejects all timeout outcomes as ambiguous. Any different treatment needs reviewed fixtures and a policy change, not relabeling a failed run. [Upstream definitions][stryker-metrics], [local implementation][local-quality]

### What the ratchet can and cannot guarantee

- Compare base and candidate over equivalent changed-file scope with identical mutator/tool/config semantics; keep new files separate and the full-repo nightly baseline separate. A repository-wide score is not a floor for every subset. Source changes can change the mutant population, so include populations/counts and introduced survivors, not only a percentage. [Spec ratchet][local-spec], [quality driver][local-quality]
- **New-file initialization has no fixed floor today.** It can preserve weak tests indefinitely if only “not worse than itself later” is checked. **Proposed Gate 1 addition:** review new/introduced survivors against critical requirements, preserve assertion tests for protected behaviors, and calibrate a new-code rule only from representative cases. An aggregate increase must not excuse losing a security-critical assertion. [Current initialization branches, lines 531–539 and 573–584][local-quality]
- Some mutants are **behaviorally equivalent**. Stryker's documentation says it cannot generally determine equivalence automatically; 100% mutation score is therefore not a universally attainable requirement. The general equivalents page discusses ignore limitations, but pinned StrykerJS documents comments, mutator exclusions and ignore plugins—do not infer that all versions lack suppression. Superman's no-waiver policy must govern any such mechanism. [Equivalent mutants][stryker-equivalent], [pinned disable mechanisms][stryker-disable], [ADR 0004][local-adr4]
- Do not “fix” equivalent mutants by weakening production behavior, deleting tests, adding dummy kills, excluding mutators or author-added ignore comments. Record an exact equivalence argument for human review; if measurement policy genuinely needs adjustment, route it through a separate Gate 1 decision. Show raw outcomes; do not secretly shrink the denominator. [No-waiver contract][local-adr4]

### Practical PR versus nightly strategy

1. **PR:** run forced base/candidate comparisons on the approved changed-existing-file scope, new files separately, plus additional mutation impact when tests/dependencies/fixtures/config changes invalidate affected prior evidence. Use the existing process/CLI seam; a surviving process-boundary mutant is not measured just because a unit import test passed. The Vitest runner defaults to import-related selection and warns that API/integration tests without direct imports need different treatment. [Pinned Vitest-runner docs][stryker-vitest], [local testing decisions][local-spec]
2. **Reuse only evidence with a complete input model.** Stryker explicitly does not detect changes outside mutant/test files, including dependencies, environment and `.snap` files; static mutants have further limitations. A “full report” may contain reused results outside the fresh mutation scope. Its incremental JSON is not a self-authenticating coverage/completion ledger. [Pinned incremental docs][stryker-incremental]
3. **Nightly:** force uncached full execution and compare the separate full-corpus baseline. `--force` reruns mutants in scope; the chosen scope must actually be full. Preserve the local TS7-compatible disposable-snapshot route: the documented bootstrap uses `--inPlace --force` **inside its owned snapshot**, not the caller checkout or an assumed working default Stryker sandbox. [Local evidence][local-bootstrap-evidence], [upstream force semantics][stryker-incremental]
4. **Bound cost without inventing green.** Use explicit worker/time budgets and report actual counts, scope, duration and outstanding work. A required run that exceeds its budget fails/blocks or waits for the required execution; sampling/rotating advisory batches must not masquerade as the complete required G6 comparison. Nightly failures detect a problem after merge; they do not retroactively prevent it. [Existing no-waiver/raw-gate contract][local-spec]

## 7. Zero-trust enforcement design and residual threat model

### Three different claims

1. **Policy cannot be changed by the candidate being judged:** independently governed policy/evaluator selection.
2. **The declared computation actually ran on the declared input:** execution isolation, trusted supervision and authenticated evidence.
3. **The candidate is correct:** not established by 1 + 2, test coverage, mutation score, static-analysis silence or agent review.

GitHub explicitly warns that artifact attestations establish provenance, **not that an artifact is secure**. SLSA 1.2's unforgeable-provenance requirement separates the trusted control plane and signing material from user-defined build steps; it does not certify test-oracle semantics. These are design precedents, not a claim that Superman already meets a SLSA level. [GitHub][gh-attest], [SLSA][slsa]

### Candidate-controlled attack surface

Assume the PR author can change source, tests/assertions, fixtures, snapshots, generated outputs, package scripts, configuration discovery/includes, exclusions, source suppression directives, baselines, workflows and fabricated reports. Imported tests/config/plugins may run arbitrary code: monkeypatch reporters/instrumentation, exit early, write artifacts, alter writable dependencies/PATH/env, spawn descendants or attack other stages on the same OS. A high score can also be obtained honestly against weak or test-aware behavior. **No hostile execution was performed here; this is the requested threat model, not a certified exploit list.** [Relevant tool controls][vitest-coverage-config], [Stryker reuse limits][stryker-incremental], [GitHub untrusted-code guidance][gh-secure]

Current `runOwned` provides `spawnSync`, POSIX process-group cleanup and timeouts, not capability isolation. `ownedSnapshot` symlinks dependency directories/binaries to the caller installation. G2 project execution and later tool stages can use the same root/job. Credential filtering, fresh directory names and postflight hashes are useful hygiene, but are not evidence that a malicious child cannot affect the checker/analyzer before the hash is examined. [Replay lines 18–66][local-replay], [raw driver][local-raw], [direct gates][local-direct], [workflow][local-ci]

### Recommended separation of responsibilities

| Boundary | Recommended ownership and evidence | What it does not prove |
| --- | --- | --- |
| **Trusted admission/controller** | Owner-governed service or protected workflow selects an immutable approved **policy/evaluator revision R** independently of candidate input. It obtains PR/event identities from the forge, selects exact H/B/M or queue subject, and decides required gates. A proposed evaluator update is evaluated by the previously trusted authority and separately reviewed before R changes. | A base-owned file is not isolated merely because it came from base. The PR must not be able to overwrite/execute inside its policy, tools, workdir or supervisor. |
| **Static-analysis workers** | Pinned analyzers and trusted rules/configs treat candidate source as **data**; mount policy/toolchain read-only and avoid executing candidate scripts/configuration. Use explicit config/discovery/input inventories. Archgate's executable rule code must come from R for independent evaluation. | Config/plugin loaders can themselves execute project code. A tool named “static” is not automatically safe; loaders need containment or trusted replacements. Parser/tool vulnerabilities remain in the trusted computing base. |
| **Dynamic-test workers** | Untrusted project/tests/build/config run in fresh disposable OS-isolated workers with narrowly bounded filesystem/network/process capabilities. No human credentials, signing key, OIDC/signing/check-writing token, privileged socket or writable trusted tool mount. Keep trusted supervisor/publication outside that capability boundary. | Same-runtime tests may tamper with in-process reporters/instrumentation or special-case known tests. Read-only tool files alone do not make observed JavaScript counters semantically independent. |
| **Behavioral oracles** | Owner-controlled acceptance/negative/regression tests and contract inputs, not replaceable by the PR. Hidden/held-out cases can strengthen evidence; evaluate through the real CLI/API/process boundary where feasible. | Hidden tests are not a universal adversarial attestation mechanism. Execution can expose them, test-aware code can evade finite cases, and the specification/oracle may itself be wrong. |
| **Evidence verifier / publisher** | Separate trusted identity validates expected gate/leg completeness, actual producer/workflow/run/attempt/event/revisions, policy/tool/input identities, inventories and report schemas/counts; only it can publish required admission. Treat dynamic artifacts as bounded untrusted data, not commands or executable evidence. | Signing a candidate-generated “pass” authenticates those bytes, not their truth. A schema-valid score does not establish oracle quality or prevent all reporter spoofing. |

**Trusted computing base:** repository/organization controls and administrators; approver identity; controller and publisher; approved policy/test oracles; analyzers/compiler/runtime and their verified supply chain; worker isolation/kernel/hypervisor; forge identity/API semantics; evidence storage/verifier. The agent and candidate project/test code are outside it. Reducing agent trust moves trust into these components—it does not remove trust. SLSA's platform model similarly includes the hardware/software/persons/organizations able to influence execution. [SLSA][slsa]

### GitHub admission, workflow and runner requirements

All following points are **recommended acceptance obligations**, not verification of current hosted settings:

- **Bind the exact tested subject.** Distinguish reviewed head **H**, tested base **B** and actual integration/merge result **M**. Verify their relationship/parents and the evaluator's actual checkout, not just candidate-supplied environment/receipt values. A fresh head, changed base, policy revision or different merge group invalidates affected evidence. Preserve exact-head approval and strict freshness, or evaluate the actual merge queue subject and required preceding queue changes. A squash result is another commit, not evidence H = M. [Local SHA contract][local-adr1], [GitHub required-check semantics][gh-checks], [protected branches][gh-protection]
- **Require the right producer, not just a familiar name.** Use protected required checks/rules and the expected GitHub App; additionally verify workflow identity/revision, event, repository, run/attempt and evaluated SHA. The shared `github-actions` App identity alone cannot distinguish a trusted evaluator from another candidate-controlled workflow with the same check name. Keep status/check-write credentials out of untrusted project jobs. [GitHub expected-source control][gh-protection], [local bootstrap binding][local-bootstrap]
- **Fail closed on absent work.** GitHub accepts `success`, `skipped` and `neutral` in relevant required-check semantics; a conditionally skipped job can report success. An always-run trusted aggregator must explicitly reject failed/cancelled/skipped/missing required dependencies and missing reports, and distinguish a trusted applicability decision from “the tool saw zero files.” A path-filtered whole workflow instead remains pending; do not create a path to a fake success. [Troubleshooting required checks][gh-checks]
- **Handle merge queues explicitly.** If adopted, require the `merge_group` trigger and evidence for its SHA; PR-only success does not establish queue success. The current bootstrap declares PR/schedule, not merge-group handling. [GitHub][gh-checks], [local workflow][local-ci]
- **Run evaluation from trusted instructions.** Candidate code may be checked out as data or passed to isolated workers; it must not choose/replace the evaluator. A pinned reusable workflow called by an editable PR workflow is insufficient if the caller can omit it or forge the required context. Verify the available host's actual enforcement features and permissions instead of assuming a particular plan/ruleset protects workflows. [GitHub required-source behavior][gh-protection], [secure use][gh-secure]
- **Do not solve this with privileged PR execution.** Fork PR workflows normally receive a read-only token and no ordinary secrets, but still execute untrusted code. `pull_request_target` and privileged `workflow_run` processing are dangerous when checking out/executing PR content or trusting its artifacts/caches. Keep privileged metadata/publication jobs free of project execution; never check out the PR into a secret-bearing `pull_request_target` job. [GitHub event/security documentation][gh-events], [secure use][gh-secure]
- **Isolate stages, not just runs.** A fresh runner can still allow a malicious project step to corrupt later static/evaluator stages within the same job. For self-hosted execution, prove single-job ephemeral registration **and clean VM/environment replacement**, no shared writable volumes/host sockets/credentials or sensitive network access, and external lifecycle/image evidence. GitHub warns that ephemeral/JIT registration alone does not clean reused hardware. Routing labels and image strings are not isolation proofs. [GitHub self-hosted guidance][gh-secure], [spec §8][local-spec]
- **Pin the real execution chain.** Verify analyzer/action/compiler/runtime artifacts, lock/config inputs and immutable image/source identities; suppress untrusted installation lifecycle/config execution in privileged contexts. The existing frozen, lifecycle-suppressed bootstrap install is useful but does not prevent tests or executable configs from running arbitrary code later. [Workflow][local-ci], [GitHub dependency/security guidance][gh-secure]

### Caches, reports and provenance

**Recommendation:** separate dependency caches from reusable gate evidence. Do not put credentials in either; GitHub documents that PRs, including forks, can read eligible base caches. A partial `restore-keys` match is an optimization for dependencies, **not valid exact-input evidence**. Verify resolved package/artifact integrity before executing cached tools. [GitHub cache reference][gh-cache]

For gate-result reuse, bind exact source/test/fixture/dependency/graph/config/policy/tool/runtime/platform inputs and the trusted producer; only trusted isolated runs may populate the trusted evidence namespace. PR workers must not write it. Invalidate on changes to any modeled input; unknown graph/config/environment effects fall back to uncached full execution. Content-addressing alone is insufficient when an untrusted producer can choose the content or attest false counters. Keep nightly uncached, and quarantine bad cache evidence rather than silently trusting a later green. [Spec/ADR coverage and cache contract][local-spec], [ADR 0014][local-adr14], [Stryker documented blind spots][stryker-incremental]

Reports need owned output paths, canonical file/source identities, size/schema/count validation, no symlink/path-traversal/command interpretation, unambiguous producer/run/attempt/SHA binding, and explicit incomplete outcomes. Obtain execution identity/status from the trusted supervisor/forge, not parsed project stdout or an artifact filename. Such provenance makes a report attributable; it **does not** make arbitrary project tests/reporters independent. GitHub's artifact-attestation warning applies even to cryptographically valid output. [Local receipt contract, §5.5][local-spec], [GitHub][gh-attest], [SLSA control-plane requirements][slsa]

**Residual limitation:** even a protected outer supervisor cannot, without a carefully bounded measurement architecture, certify every in-process coverage/mutation counter produced alongside adversarial code. Independently enforced static constraints, immutable test inputs, separately observed CLI behavior and protected admission are achievable increments. A claim of fully adversarial dynamic-metric attestation or general correctness would need a substantially stronger argument than this research or v0 provides.

## 8. Adoption, ratchets and concrete acceptance checks

### Phases and decisions

1. **Preserve the current admission status.** Finish existing Gate 1 prerequisites and actual three-platform/runner evidence; do not convert this research, a lint pilot or historical local results into readiness. Decide explicitly whether the human-reviewed PR-owned checker remains an accepted v0 limit or ADR 0001 is reopened. [README][local-readme], [spec §17][local-spec]
2. **Measure without changing the bar.** Pilot Biome's 15/50/4 triggers over declared runtime/test cohorts, inspect the 47 local diagnostics (§2), inventory graph/coverage gaps and review representative mutation survivors. Record useful fixes, false positives, review effort and latency. Existing bootstrap validation functions and declarative/test code should not be fragmented just to make numbers green. [NIST design caution][nist-pdf], [static-analysis experience][static-study]
3. **Promote concrete policy through Gate 1.** Explicit error severities and zero violations for high-signal safety/architecture rules; calibrated structural no-new/no-worse rules only where useful. Preserve the selected overall coverage contract; any per-file/diff/new-code mutation requirement needs a separate explicit decision. Add actual failing/passing fixtures before declaring a new gate authoritative. [No-waiver ADR][local-adr4]
4. **Protect and validate baselines.** Read the approved baseline from trusted base/policy state, not a candidate's replacement. Bind tool, rule semantics, cohort, inventory, graph and metric definitions. Compare like with like; reject deleted metric keys, renamed/unmodeled scope substitutions and a “tightening” not supported by fresh measurement. Rebaseline tool/metric migrations in a dedicated reviewed policy change, not an implementation PR. Existing ticket tightening permissions remain bounded to the spec's mutation/duplication rules. [Spec §§5.3–5.4][local-spec], [quality evidence][local-bootstrap-evidence]
5. **Harden authority and execution before advertising agent-independent enforcement.** Demonstrate the §7 boundaries with adversarial fixtures and actual host/worker evidence. An independent agent review is supporting review only; it cannot authenticate a check, approve as André or become the trusted evaluator merely by running in fresh context. [Existing identity contract][local-adr1]
6. **Optimize only with demonstrated scope safety.** Retain complete pre-merge evidence for required guarantees; allow exact-input reuse/affected selection only after the provider proves its closure and fallback contract. Full nightly runs detect drift and accepted blind spots; inspect real misses and escaped defects rather than optimizing a composite quality score. [Spec §5.7][local-spec]

### Exception process compatible with Superman's no-waiver decision

There is **no ordinary owner-approved inline exception** to recommend here. An agent raises a rule conflict and stops; André may approve a separate **spec-kind Gate 1** change to the governing rule/policy. A useful narrow proposal identifies the rule, exact scope, accountable owner, reason, alternative safeguards, evidence/fixtures and review/expiry condition. It becomes effective only after that policy change is approved/admitted—not by a PR comment, agent-authored ignore, runtime flag or changing the baseline inside the feature. [ADR 0004][local-adr4]

For structural rules, a centrally defined distinction for a genuinely cohesive dispatch table/test cohort may be justified; it must not become a broad runtime exclusion. This report does **not** recommend new coverage-ignore or mutation-disable exceptions to obtain 100%, nor silently introduce a waiver mechanism. Expired/unmodeled policy needs a fresh decision rather than an automatic pass. [Existing policy][local-spec]

### Acceptance checks for a later authorized policy/evaluator change

These are observable acceptance criteria, **not experiments completed by this research**:

| ID | Required observation |
| --- | --- |
| A1 — policy tampering | A PR changes checker code, workflow, lint severity, include/exclude/config discovery, a fixture loader, package script or baseline to hide a planted violation. The independent authority still applies the approved policy or blocks the unmodeled change; candidate-produced “pass” is insufficient. |
| A2 — severity/scope | A >15 cognitive fixture fails only after its intended blocking severity is explicit; the same negative control cannot pass merely as info with `--error-on-warnings`. Unknown language, skipped large file, parse error, zero analyzed files or unexpected ignore is reported/blocked according to the complete inventory contract. |
| A3 — coverage counts | An unloaded module declaring many functions contributes its real AST denominator; a partially exercised conditional contributes uncovered branches. All four exact aggregate ratios are checked independently. A below-90 ratio displayed as rounded 90 fails; 90–99.99 is below target, not automatically below the current floor. |
| A4 — evidence invalidation | Change only tests, fixtures/snapshots, policy, dependency graph, instrumentation/runtime or a source-map input. Reused coverage/mutation evidence is invalidated as applicable; unknown coverage evidence forces uncached full execution, not changed-files-only substitution. |
| A5 — mutation completion | Exercise Killed, Survived, NoCoverage, Timeout, CompileError, RuntimeError, Ignored, Pending, zero mutants and truncated/inconsistent reports. Outcomes match the current conservative driver; no-coverage is not dropped or timeout promoted to a local success. |
| A6 — new-code/average gaming | Introduce a weak new file and separately remove a critical assertion while adding easy mutant kills. Reports expose initialization and specific introduced survivors. Any new blocking response comes from an explicitly adopted new-code/behavior policy, not a fictional existing absolute floor. |
| A7 — graph/contract integrity | Resolve aliases/reexports/type-only versus runtime cycles correctly; deliberately unknown dynamic edges do not produce a “complete zero” graph. Forbidden layer access/public API incompatibility fails; an approved valid dependency remains green. |
| A8 — integration identity | New head after approval, base advancement, wrong evaluated tree, stale result, different policy R or merge-group SHA all prevent stale admission. Verify expected workflow/App/run/attempt and M's relationship to H/B from independent forge evidence. |
| A9 — missing/skipped checks | Missing artifact, conditional skip, cancelled matrix leg, neutral result and selected-subset receipt cannot satisfy the full required manifest. Legitimate non-code applicability is a trusted explicit `n/a`, not a made-up tool pass. |
| A10 — worker boundaries | Controlled hostile test/config attempts cannot write trusted tools/rules/supervisor/admission artifacts, reach credentials/check-writing authority, poison trusted caches or persist into later workers. Prove actual OS/network/filesystem boundaries, not only path names/process-group cleanup. A failed attack probe still does not prove all dynamic counters unforgeable. |
| A11 — determinism and budgets | Repeat identical approved inputs with recorded tool/runtime/platform identities; stable inventories and metric counts are reproducible. Flakes, timeouts and partial budget runs remain explicit failures/incompleteness, not retry-until-green or sampled full passes. |
| A12 — rollout evidence | Actual required native-platform jobs, tool-asset acceptance and host protection/runner lifecycle settings are independently verified. A local report, declared matrix or historical arm64 candidate build does not close the current Gate 1 blockers. |

### Portability to the spec's other languages

Port the **policy/evidence contract**, not TS defaults or a dashboard's overall score. The spec names TS/JS, Elixir, Rust, C#, Python and Haskell providers, with Go/deploy work post-v0. Each adapter must declare complete compile/test projects, source/branch/function measurement semantics, mutation operators/statuses where supported, command/tool identities and fail-closed unknown-input behavior. Reuse that ecosystem's existing compiler/linter/test tools; do not mandate a polyglot suite solely for metric uniformity. [Spec §§5.7, 16][local-spec]

A language/provider exposing only three metrics must not relabel one as a distinct fourth, and a token-based complexity estimate must not inherit another implementation's function cutoff. Cross-runtime/process coverage, mutation activation and source mapping need new fixture evidence; changing runtime/tool identity invalidates prior measurement assumptions. No alternate-language/runtime/tool compatibility was tested or adopted here.
